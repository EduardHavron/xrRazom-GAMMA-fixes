# FX-TURNIN: пир не получает заново сданные задания
Статус: действует        Мод: `zz xrRazom Fix - Turned-in Task Sync`        Скрипт: `gamedata/scripts/zz_xrrfix_task_sync.script`
Где ставить: пир (на хосте безвреден)        Зависит от: xrRazom Co-op 1.4 (`xrr_net_client`: `_G.OnPlayerTask`, `_G.OnJoinTask`, `_G.OnTaskSyncWith`)        Лог-маркер: `[XRRFIX] tasksync: stage-255 guard installed`

## Проблема
Пир сдал повторяемое задание, а после очередной синхронизации (подключение, синхронизация задания с хостом) оно снова
появляется у него в списке активных, хотя у хоста уже сдано.

## Причина
- По истории (в Lua-коде xrRazom не видно, логика стадий — в `task_objects` Anomaly): выполненное повторяемое задание остаётся в
  `task_manager.task_info` хоста со стадией `255` до истечения таймаута повтора.
- Хост рассылает состояние заданий; у пира приём идёт через глобальные обработчики `xrr_net_client.script`:
  - `OnPlayerTask(player_netid, task_id, task_giver, task_mid, task_state, task_stage, ...)`
  - `OnJoinTask(task_id, giver_id, stage, target_id, ...)` (пакетная выдача при подключении)
  - `OnTaskSyncWith(netid, task_id, giver_id, stage)`
- Каждый из них, если у пира нет `tm.task_info[task_id]`, вызывает `apply_remote_task(tm, task_id, giver, ...)` — т.е. выдаёт
  задание заново, и только потом выставляет `tsk.stage = <stage>`. Состояние «сдано» (stage 255) этим путём превращается
  в новую выдачу.

## Решение
В `on_game_start` (под `pcall`) модуль `xrr_net_client` принудительно загружается (чтобы его `_G.*` уже существовали),
затем каждая из трёх глобальных функций заменяется обёрткой:
- позиции аргументов: `OnPlayerTask` — id=2, stage=6; `OnJoinTask` — id=1, stage=3; `OnTaskSyncWith` — id=2, stage=4;
- если `stage == 255` и машина не хост (`not XrrIsHost()`), и у пира нет активного задания (`tm.task_info[task_id]` отсутствует
  или у него нет `t` — игрового объекта задания), вызов отбрасывается с логом
  `tasksync: <name> ignored turned-in task <task_id> (stage 255)`;
- во всех остальных случаях вызывается оригинал с теми же аргументами.
Если какой-то глобал отсутствует — лог `tasksync: _G.<name> missing, skipped`, остальные оборачиваются.

Предполагается (не проверяемо в Lua — вызов идёт из C++), что движок находит обработчики по имени в `_G` в момент вызова.

## Требования
### FX-TURNIN-001 Сданное задание не выдаётся заново  [auto]
У пира синхронизация со стадией 255 для задания, которого у него нет, НЕ ДОЛЖНА вызывать оригинальный обработчик.
- Дано `XrrIsHost() == false`, `task_manager.get_task_manager().task_info = {}`, заглушки трёх оригиналов
  Когда вызываются `OnPlayerTask(1, "T", 5, 0, 0, 255)`, `OnJoinTask("T", 5, 255, 0)`, `OnTaskSyncWith(1, "T", 5, 255)`
  Тогда ни один оригинал не вызван, в логе три строки `ignored turned-in task T (stage 255)`.

### FX-TURNIN-002 Активное задание получает стадию 255  [auto]
Если у пира задание активно (`task_info[id].t` есть), синхронизация со стадией 255 ДОЛЖНА пройти в оригинал.
- Дано `task_info["T"] = { t = {} }`, не хост
  Когда вызывается `OnTaskSyncWith(1, "T", 5, 255)`
  Тогда оригинал вызван с теми же четырьмя аргументами.

### FX-TURNIN-003 Прочие стадии не фильтруются  [auto]
Обёртка НЕ ДОЛЖНА влиять на синхронизации со стадией, отличной от 255, и ДОЛЖНА возвращать результат оригинала.
- Дано `task_info = {}`, не хост
  Когда вызывается `OnPlayerTask(1, "T", 5, 0, 0, 1, <доп. аргументы>)`
  Тогда оригинал вызван со всеми аргументами (включая хвостовые), его возвращаемые значения проброшены.

### FX-TURNIN-004 Хост не фильтрует  [auto]
На хосте обёртка ДОЛЖНА всегда вызывать оригинал.
- Дано `XrrIsHost() == true`, `task_info = {}`
  Когда вызывается любая из трёх функций со стадией 255
  Тогда оригинал вызван.

### FX-TURNIN-005 Повторное подключение после сдачи  [manual]
Пир, сдавший повторяемое задание, НЕ ДОЛЖЕН видеть его снова активным после переподключения, пока хост держит его на стадии 255.
- Дано пир сдал повторяемое задание T, у хоста T ещё на стадии 255 (таймаут повтора не истёк)
  Когда пир выходит и заново подключается к хосту
  Тогда T нет в активных заданиях пира; в логе пира `[XRRFIX] tasksync: OnJoinTask ignored turned-in task T (stage 255)`.

## Безопасность
- Нет xrRazom — глобалов нет, каждая обёртка пропускается с логом `missing, skipped`; строка `stage-255 guard installed` всё
  равно пишется (это не признак успешной установки всех трёх).
- Соло/хост: на хосте `XrrIsHost()` истинно — оригиналы вызываются без изменений; в соло обработчики не вызываются.
- Защиты от повторной установки нет: второй `on_game_start` обернёт обёртку. Поведение то же, лог об отброшенном вызове может
  дублироваться.

## Вне области / известные ограничения
- Значение 255 как «сдано» взято из истории/логов, в Lua-коде xrRazom и модов оно не встречается (константа в `task_objects` Anomaly).
- Фикс не убирает уже выданное повторно задание у пира, если оно пришло до установки фикса.
- `OnForcedTaskState` (терминальные состояния) не трогается.
- Если пир действительно должен получить задание на стадии 255 без активной копии (такого сценария в xrRazom не найдено) — оно будет отброшено.

## Проверка в игре
1. Пир запускает игру. Лог: `[XRRFIX] tasksync: stage-255 guard installed` и нет строк `missing, skipped`.
2. Пир берёт и сдаёт повторяемое задание (например, simulation_task_*), хост видит его завершённым.
3. Пир переподключается (или хост делает действие, вызывающее синхронизацию заданий).
4. Лог пира: `[XRRFIX] tasksync: OnJoinTask ignored turned-in task <id> (stage 255)` (или `OnPlayerTask`/`OnTaskSyncWith`).
5. В PDA пира задание не появляется среди активных.
