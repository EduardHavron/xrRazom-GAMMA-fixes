# Общая картина: распространение фиксов xrRazom
Статус: действует        Код: `host/publish.ps1`, `installer/install.ps1`, `agent/xrrfix_agent.ps1`, `.github/workflows/release.yml`, `.github/scripts/build_pack.py`

## Назначение

Репозиторий раздаёт локальные моды-фиксы для кооператива xrRazom 1.4 на сборке S.T.A.L.K.E.R. G.A.M.M.A.
(Mod Organizer 2, portable; у хоста — `D:\Games\Gamma`). Играют двое; xrRazom при входе сверяет набор модов
хоста и пира побайтно и не пускает при расхождении. Поэтому цель системы — чтобы фиксы одной секции MO2 у обоих
игроков были **байт-в-байт одинаковыми**, а публиковать мог любой из двоих, не откатывая изменения другого.

Этот документ задаёт роли, компоненты, поток данных, сквозные инварианты и глоссарий. Детали — в
`repo-layout.md` (REPO), `publish.md` (PUB), `ci-release.md` (CI), `installer.md` (INS), `agent.md` (AGT).

## Термины

| Термин | Значение |
|---|---|
| Секция | Группа модов профиля MO2 под разделителем с именем секции (по умолчанию `xrRazom Sync`). В `modlist.txt` моды идут от высшего приоритета к низшему; моды секции — строки **над** строкой `<секция>_separator` до предыдущей строки `*_separator` (или до шапки `# ...`). |
| Разделитель | Псевдо-мод MO2 с именем `<секция>_separator` (строка `+xrRazom Sync_separator` в `modlist.txt`, папка `mods\xrRazom Sync_separator\` с `meta.ini`). |
| Список (list) | Упорядоченный список имён модов секции: порядок = приоритет, первый — высший. В репозитории хранится в `pack/pack.json` → `mods`. |
| Включённые моды секции | Строки секции с префиксом `+`. Только они публикуются. |
| Маркер | Файл `xrrfix_pack.txt` в корне папки мода, текст `xrRazom fixes pack <версия>`. Означает «мод поставлен нашим пакетом» (установщик выключает такие моды, если их больше нет в пакете). Никогда не публикуется и не участвует в сравнении. |
| meta.ini | Служебный файл MO2 в корне папки мода. Не публикуется и не участвует в сравнении (только верхний уровень папки мода). |
| Ключ содержимого | Отсортированный набор пар «относительный путь → git blob id» всех файлов мода, кроме верхнеуровневых `meta.ini` и `xrrfix_pack.txt`. Два мода равны ⇔ равны ключи ⇔ файлы совпадают побайтно. |
| L / B / R | Три состояния при публикации. **L** — локальный MO2 (включённые моды секции, их файлы, порядок). **R** — `origin/main` (точнее, upstream текущей ветки) после `git fetch`. **B** — база: `git merge-base HEAD R`, последнее общее состояние этой машины и GitHub. Для каждого мода и для списка — свой L/B/R. |
| База (merge-base) | См. B. Фиксирует «что эта машина уже видела»: всё, что отличается от B только в R, — чужое изменение; только в L — своё. |
| Догон (catch-up) | Шаг publish: изменения, сделанные только на GitHub, ставятся в локальный MO2 (через `installer/install.ps1` на временном пакете) **до** публикации своих изменений. |
| Конфликт | Мод (или порядок списка) изменён и локально, и на GitHub, и результаты различаются. Publish останавливается (код 3) и ничего не меняет. |
| Версия релиза | `ГГГГ.ММ.ДД-N`: дата сборки по UTC и `github.run_number` (сквозной счётчик запусков workflow, **не** счётчик за день). Тег `v<версия>`, заголовок `xrRazom fixes <версия>`, ассет `xrRazom_fixes.zip`. Пример: `v2026.10.13-4`. |
| Sync-версия | `sync-<7 символов sha R>` — версия временного пакета догона; попадает в маркеры у публикующего. |
| Пакет | `xrRazom_fixes.zip` релиза или временная папка догона: `pack.txt` + `install.ps1` + `mods/<имя>/…`. |

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| Хост | владелец репозитория (EduardHavron), хост сессий xrRazom | Правит фиксы в своём MO2, публикует `host\publish.bat`. Имеет git-клон. |
| Пир (друг) | collaborator с правом записи (KDVFirehawk) | Получает релизы агентом. Если у него есть git-клон и `publish.bat`, он **тоже публикующий** — права и поведение те же, что у хоста. |
| Публикующий | любой с клоном и правом push | Запускает `publish.ps1`; отличий «хост/друг» в коде publish нет. |
| Агент, режим пира | `agent\xrrfix_agent.ps1` по Планировщику заданий, машина без клона | Раз в 10 минут проверяет последний релиз, при закрытых MO2/игре ставит его установщиком. |
| Агент, режим хоста | тот же агент на машине с git-клоном репозитория | Вместо релизов запускает `host\publish.ps1 -SyncOnly -NoWait -NoPrompt` (только догон, без публикации). |
| CI | GitHub Actions `release.yml` | Проверяет `pack.json` и синтаксис Lua, собирает zip, создаёт релиз, шлёт уведомление в Discord. |

## Компоненты и поток данных

```
 MO2 публикующего: profiles\<p>\modlist.txt, секция "xrRazom Sync", mods\<имя>\
        │  host\publish.ps1  (3-стороннее сравнение L/B/R)
        │   1) догон: только-удалённые изменения → временный пакет → installer\install.ps1 → свой MO2
        │   2) git fast-forward / rebase до R
        │   3) публикация: только-локальные изменения → mods/, pack/pack.json → commit → pull --rebase → push
        ▼
 GitHub main (публичный): mods/<имя>/…, pack/pack.json
        │  push в main (пути mods/, pack/, installer/, agent/, CI) → release.yml
        │  validate (pack.json, LuaJIT -b, XML-предупреждения) → build → gh release create --latest → Discord
        ▼
 Release v<ГГГГ.ММ.ДД-N>: xrRazom_fixes.zip (pack.txt, install.*, README.txt, mods/, agent/)
        │  агент (режим пира), каждые 10 мин, GitHub API releases/latest
        ▼
 installer\install.ps1 → MO2 получателя: заменяются папки модов пакета, пересобирается только секция

 Машина с клоном: агент (режим хоста) → publish.ps1 -SyncOnly -NoWait -NoPrompt → шаги 1–2 выше
```

## Входы и выходы

- Входы системы: `modlist.txt` профиля MO2 и папки `mods\<имя>\` у публикующего; `host/publish.ini`; содержимое `main`.
- Выходы: коммиты в `main` (только `mods/`, `pack/`), релизы GitHub, изменённая секция MO2 у получателей,
  `modlist.txt.xrrfix.bak` (копия до установки), маркеры `xrrfix_pack.txt`.
- Машиночитаемые строки stdout publish (для агента): `XRRFIX_SYNC_RESULT: …`, `XRRFIX_SYNC_CONFLICT: …` (см. PUB).
- Коды выхода publish/installer: 0 ок, 1 ошибка, 2 отложено, 3 конфликт (только publish).

## Требования

### SYS-001 Единый источник истины  [auto]
Содержимое раздаваемого пакета ДОЛЖНО определяться только коммитом ветки `main`: папками `mods/<имя>/` для имён из
`pack/pack.json` → `mods`, в порядке этого списка.
- Дано коммит, где `pack.json` перечисляет моды A, B, а в `mods/` есть ещё папка C. Когда CI собирает релиз из этого
  коммита. Тогда в zip есть `mods/A/…`, `mods/B/…` (в этом порядке в `pack.txt`) и нет `mods/C/`.

### SYS-002 Байт-в-байт  [auto]
Файлы мода ДОЛЖНЫ проходить путь «MO2 публикующего → репозиторий → zip релиза → MO2 получателя» без изменения байтов
(без перекодировки строк, BOM, нормализации CRLF/LF); исключение — верхнеуровневые `meta.ini` и `xrrfix_pack.txt`.
- Дано мод с файлами в CRLF, LF, с BOM и бинарным файлом. Когда он опубликован, собран CI и установлен у получателя.
  Тогда SHA-256 каждого файла мода у получателя (кроме `meta.ini`, `xrrfix_pack.txt`) совпадает с исходным у публикующего.

### SYS-003 Публикуются только включённые моды секции  [auto]
В `pack.json` и `mods/` НЕ ДОЛЖНЫ попадать моды вне секции и выключенные (`-`) моды секции.
- Дано секция содержит `+A`, `-B`, а над разделителем предыдущей секции есть `+C`. Когда выполняется первая публикация с `-Yes` (в `pack.json` B и R этих модов нет).
  Тогда `pack.json` → `mods` = `["A"]`.

### SYS-004 У получателя меняется только секция  [auto]
Установка ДОЛЖНА менять в профиле получателя только блок секции; моды вне секции НЕ ДОЛЖНЫ менять положение и состояние,
кроме исключений, описанных в `installer.md` (мод пакета, найденный вне секции, переезжает в неё; включённый мод с маркером
вне секции, которого нет в пакете, выключается).
- Дано `modlist.txt` получателя с чужими модами выше и ниже секции. Когда ставится пакет. Тогда строки чужих модов
  (вне секции, без маркера, не из пакета) остаются в прежнем относительном порядке и с прежним `+`/`-`.

### SYS-005 Публикация не откатывает чужие изменения  [auto]
Публикация НЕ ДОЛЖНА заменять в `main` мод (или порядок списка), который со времени базы B менялся только на GitHub,
локальной копией публикующего.
- Дано друг опубликовал новую версию мода A, у хоста в MO2 старая A (= B) и изменённый мод D. Когда хост запускает publish.
  Тогда в новом коммите хоста A = версия друга, D = версия хоста, а в MO2 хоста стоит A друга.

### SYS-006 Конфликт требует решения человека  [auto]
Если мод или порядок изменены и локально, и на GitHub по-разному, publish ДОЛЖЕН завершиться с кодом 3, ничего не меняя
в MO2 и не создавая коммитов, пока человек не выберет сторону (`-TakeRemote` / `-TakeLocal`).
- Дано A изменён и у хоста, и у друга (разное содержимое). Когда хост запускает publish без `-Take*`. Тогда код 3,
  `HEAD` и `modlist.txt` хоста не изменились, в выводе есть `XRRFIX_SYNC_CONFLICT: mods=A`.

### SYS-007 Догон до публикации  [auto]
Только-удалённые изменения ДОЛЖНЫ быть поставлены в MO2 публикующего до того, как его локальные изменения попадут в коммит,
и до сдвига локального `HEAD` к R.
- Дано на GitHub изменён A, локально изменён D. Когда publish отрабатывает. Тогда сначала установщик ставит A (в выводе
  `XRRFIX_SYNC_RESULT: installed=1 mods=A`), затем создаётся коммит только с D.

### SYS-008 Паритет проверки модов  [manual]
После того как последний релиз установлен у пира, а у хоста выполнен догон до того же коммита, набор включённых модов секции,
их порядок и байты файлов (кроме `meta.ini`/маркера) ДОЛЖНЫ совпадать у обоих, и xrRazom ДОЛЖЕН пускать пира без ошибки
проверки модов.
- Дано хост опубликовал, CI выпустил релиз, агент пира поставил его. Когда пир подключается к хосту. Тогда вход проходит
  без ошибки расхождения модов.

### SYS-009 Изменения MO2 только при закрытых MO2 и игре  [auto]
Ни publish (догон), ни установщик, ни агент НЕ ДОЛЖНЫ менять папки модов и `modlist.txt`, пока запущен процесс из списка
блокирующих (по умолчанию `ModOrganizer`, `Anomaly*`; переопределяется `XRRFIX_BLOCK_PROCS`).
- Дано запущен процесс с именем из `XRRFIX_BLOCK_PROCS`, на GitHub есть изменения. Когда агент режима хоста вызывает
  `publish.ps1 -SyncOnly -NoWait -NoPrompt`. Тогда код 2, файлы MO2 не изменены.

### SYS-010 Равноправие публикующих  [manual]
Любой участник с git-клоном и правом push МОЖЕТ публиковать тем же `host\publish.bat`; поведение publish НЕ ДОЛЖНО зависеть
от того, кто запускает (хост или друг).
- Дано у друга клон и свой `publish.ini`. Когда друг публикует изменение мода. Тогда появляется релиз, агент режима хоста
  у хоста ставит изменение в MO2 хоста.

### SYS-011 Агент на машине с клоном только догоняет  [auto]
Агент в режиме хоста ДОЛЖЕН вызывать publish только с `-SyncOnly -NoWait -NoPrompt` и НЕ ДОЛЖЕН создавать коммиты и push.
- Дано клон с локальным изменением мода D и без удалённых изменений. Когда отрабатывает тик агента. Тогда `HEAD` и
  `origin/main` не изменились, код publish 0, в выводе `XRRFIX_SYNC_RESULT: installed=0 mods=`.

### SYS-012 Релиз только после проверки  [auto]
Релиз ДОЛЖЕН создаваться только после успешной проверки `pack.json` и синтаксиса Lua; при неудаче получатели ДОЛЖНЫ оставаться
на прошлой версии (подробно — `ci-release.md`).
- Дано коммит с синтаксической ошибкой в `.script`. Когда отрабатывает CI. Тогда релиз не создан, последний релиз прежний.

### SYS-013 Публичность: что публикуется  [auto]
Репозиторий публичный; в него и в релиз ДОЛЖНЫ попадать только: файлы модов секции (без `meta.ini`, маркера),
`pack/pack.json`, скрипты репозитория. НЕ ДОЛЖНЫ попадать: `modlist.txt`, файлы профилей MO2, локальные пути, сохранения,
логи агента, содержимое `%LOCALAPPDATA%\xrrfix`. Сообщение коммита и имя/email автора коммита (из `git config`) публичны.
- Дано публикация с изменённым модом. Когда смотрим `git show --name-only HEAD`. Тогда все пути начинаются с `mods/` или `pack/`.

### SYS-014 Секреты  [auto]
Вебхук Discord ДОЛЖЕН храниться только в секрете GitHub `DISCORD_WEBHOOK`; никакие токены, пароли и вебхуки НЕ ДОЛЖНЫ
находиться в файлах репозитория, `publish.ini` и zip релиза. Агент обращается к GitHub API без аутентификации; publish
использует учётные данные git/gh пользователя, не храня их.
- Дано рабочее дерево репозитория и собранный zip. Когда ищем `discord.com/api/webhooks`, `ghp_`, `github_pat_`. Тогда
  совпадений нет.

## Ошибки и граничные случаи

- Одновременная публикация двумя людьми: 3-стороннее сравнение делается на момент `git fetch`; гонка между fetch и push
  разрешается только `git pull --rebase` (построчное слияние git), см. PUB «Открытые вопросы».
- Агент режима хоста и ручной publish на одной машине исключают друг друга через мьютекс `Local\xrrfix_publish`
  (агент запускается задачей с LogonType Interactive, т.е. в той же сессии).
- Релиз не создан (CI упал) — пиры остаются на прошлой версии, публикующий уже содержит изменения в `main`.

## Вне области

- Сами фиксы и их поведение в игре (`specs/fixes/*.md`).
- Проверка модов внутри xrRazom (как именно он сравнивает файлы).
- Моды вне секции, сборка GAMMA, обновления MO2.

## Открытые вопросы / известные ограничения

1. `README.md` устарел относительно кода: пишет, что publish «скопирует секцию в `mods/`» (сейчас публикуются только
   локальные изменения, 3-стороннее сравнение, догон, конфликты); таблица фиксов не содержит
   `zz xrRazom Fix - Kill Tracker Mirror Corpses`, который есть в `pack.json`; формат версии `vГГГГ.ММ.ДД-N` не поясняет,
   что N — сквозной `run_number`.
2. Не установлено, сравнивает ли xrRazom `meta.ini` или только `gamedata/`. Система исходит из того, что `meta.ini` и маркер
   на проверку не влияют (они различаются у хоста и пира).
3. Роль «друг публикует» в коде не отличается от хоста; если у друга есть клон, его агент тоже работает в режиме хоста
   и релизы не скачивает — он получает изменения только через `publish -SyncOnly`.
4. CONTRACT.md описывает zip без `agent/`; фактически `build_pack.py` кладёт в zip и `agent/` (самообновление агента).
