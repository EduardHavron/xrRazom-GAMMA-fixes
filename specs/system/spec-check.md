# Сверка спецификаций, тестов и документации
Статус: действует        Код: `tools/spec_check.py`, навык Claude `.claude/skills/spec-check/SKILL.md`, тест `tests/python/test_spec_check.py`

## Назначение

Механическая проверка того, что спеки, тесты, карты покрытия и README говорят одно и то же. Только читает, ничего не правит.
Ловит расхождения, которые раньше находились вручную: требование без теста, тест на несуществующее требование, README с
устаревшим именем мода, фикс без отметки о проверке в игре. Смысловую сверку (спека против кода мода) делает навык
`/spec-check` поверх этого отчёта.

## Входы и выходы

- Запуск: `python tools/spec_check.py [--root <корень репозитория>] [--json]`.
- Читает: `specs/**/*.md`, имена тестов в `tests/**` (`.lua`, `.ps1`, `test_*.py`), `tests/*/COVERAGE.md`, `README.md`,
  `specs/README.md`, `pack/pack.json`.
- Выход: по строке на находку `<УРОВЕНЬ> <CHK-NNN>  <сообщение>` и итог `spec_check: N error(s), N warning(s), N note(s)`;
  с `--json` — массив `{level, check, message}`. Уровни: `error`, `warning`, `note`.
- Код выхода: `0` — ошибок нет (предупреждения и заметки допустимы), `1` — есть ошибки, `2` — не корень репозитория или
  не читаются `pack.json` / `README.md` / `specs/README.md`.

### Где инструмент берёт ID
- Требование — заголовок `### <ID> <имя>  [auto]` или `[manual]` в `specs/**`; зачёркнутый (`### ~~<ID>`) — удалённое.
- Тест — имя случая: Lua `H.case("…")` / `H.xfail("…")` / `H.skip("…")`, PowerShell `Test-Case '…'` / `TC '…'`,
  Python — имя функции `test_<обл>_<NNN>_…` (`test_repo_017_…` → `REPO-017`) и первая строка докстринга.
- Покрытие — любой ID в `tests/*/COVERAGE.md`; запись `FX-A-005, -006` означает оба ID. В строке таблицы, где первая ячейка
  называет требование: `via <ID>, <ID>` — покрыто тестами других требований; `GAP` — тест известно, что отсутствует.

## Требования

### CHK-001 У требования `[auto]` есть тест  [auto]
Для каждого неудалённого требования `[auto]` ДОЛЖЕН существовать тест с его ID в имени. Иначе:
строка `COVERAGE.md` с `GAP` → `warning`; строка с `via` и у всех перечисленных ID есть тесты → находки нет;
иначе → `error`.
- Дано `FX-A-001 [auto]` и нет тестов. Тогда `error CHK-001`.
- Дано в `COVERAGE.md` `| FX-A-001 | via FX-A-002 |` и тест `FX-A-002 …`. Тогда находки нет.
- Дано `| FX-A-001 | GAP: … |`. Тогда `warning CHK-001`.

### CHK-002 Тест ссылается на существующее требование  [auto]
ID в имени теста, которого нет среди требований, ДОЛЖЕН давать `error`; ссылка на удалённое требование — `warning`.

### CHK-003 Карта покрытия полная  [auto]
Каждое неудалённое требование ДОЛЖНО упоминаться в каком-нибудь `tests/*/COVERAGE.md`, а `COVERAGE.md` НЕ ДОЛЖЕН называть
неизвестные ID; иначе `warning`.

### CHK-004 Проверка в игре  [auto]
У спеки каждого мода из `pack.json` (`specs/fixes/*.md`, сопоставление по полю `Мод:` шапки) в первых строках ДОЛЖНО быть
`Проверка в игре: <подтверждено | частично | не подтверждено | не проводилась | не записана>`, иначе `error`. Колонка
«В игре» таблицы «Состав пакета» в `README.md` ДОЛЖНА совпадать с этим значением, иначе `warning`. Мод без спеки — `warning`.

### CHK-005 Документация перечисляет моды пакета  [auto]
Те же правила, что REPO-017 (`repo-layout.md`), уровень `warning`. Сравнение — одной функцией `doc_mismatches`, её же
использует тест REPO-017.

### CHK-006 Пометки `[НЕ ПРОВЕРЕНО]`  [auto]
Для каждой спеки в `specs/fixes/` с пометками `[НЕ ПРОВЕРЕНО]` ДОЛЖНА выводиться `note` с их числом.

### CHK-007 Только чтение и коды выхода  [auto]
Инструмент НЕ ДОЛЖЕН создавать или менять файлы. Коды выхода и `--json` — как в «Входы и выходы».
- Дано корень без `specs/`. Тогда код `2`, сообщение в stderr.

### CHK-008 Проверка в CI  [auto]
`tests/python` ДОЛЖЕН запускать проверку на самом репозитории: ошибка → тест падает (такие ошибки появляются только из
коммитов спек и тестов, публикацию модов они не блокируют), предупреждения → `::warning` в GitHub Actions, тест проходит.

### CHK-009 Навык `/spec-check`  [manual]
Навык ДОЛЖЕН запускать `tools/spec_check.py`, разбирать каждую находку и затем сверять по смыслу изменённые спеки
(`git diff` относительно `origin/main` или указанные пользователем) с кодом модов и тестами. Навык только отчитывается;
правки — после согласия пользователя.

## Ошибки и граничные случаи
- `pack.json` с BOM читается.
- Один тест может закрывать несколько требований (`SYS-005 SYS-007 PUB-034 …`).

## Вне области
- Совпадение текста требования и поведения кода механически не проверяется — это работа навыка (CHK-009) и самих тестов.

## Открытые вопросы / известные ограничения
1. Python-тесты распознаются только по имени функции и первой строке докстринга; ID в середине докстринга не учитывается.
2. Строка `COVERAGE.md` с `via` проверяется только на то, что у указанных ID есть тесты, а не на то, что они действительно
   проверяют это требование.
