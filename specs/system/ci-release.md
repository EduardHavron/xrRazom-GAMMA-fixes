# CI: проверка, сборка и релиз фиксов
Статус: действует        Код: `.github/workflows/release.yml`, `.github/scripts/build_pack.py`

## Назначение
GitHub Actions проверяет содержимое репозитория (pack.json, синтаксис Lua, XML), собирает архив
`xrRazom_fixes.zip` для пира, публикует его как последний (latest) GitHub Release и сообщает о результате в Discord.
Релиз — единственный канал, из которого агент пира получает фиксы (см. `agent.md`); архив также несёт
установщик (`installer.md`) и файлы агента для его самообновления.

## Термины
- **Прогон** — один запуск workflow `Build & release xrRazom fixes` (job `release`).
- **VERSION** — строка `<YYYY.MM.DD>-<run_number>`, дата по UTC на момент шага сборки, `run_number` — `github.run_number`.
- **Пакет** — моды, перечисленные в `pack/pack.json` → `mods` (порядок = приоритет MO2, первый — высший).
- **Аннотация** — строка `::error file=<path>::<msg>` / `::warning file=<path>::<msg>` (в GitHub Actions,
  `GITHUB_ACTIONS=true`); вне Actions — `ERROR: <msg>` / `WARNING: <msg>`. Переводы строк в тексте аннотации кодируются `%0A`, `%` — `%25`.

## Входы и выходы
| Что | Значение |
|---|---|
| Триггеры | `push` в `main`, затронувший пути из CI-001; `workflow_dispatch` |
| Входные файлы | `pack/pack.json`, `mods/**`, `installer/install.ps1`, `installer/install.bat`, `installer/README.txt`, `agent/*` (верхний уровень) |
| Секреты | `DISCORD_WEBHOOK` (необязателен), `github.token` (автоматический) |
| Окружение | `CI=true` (делает LuaJIT обязательным), `GITHUB_ACTIONS=true` (формат аннотаций) |
| Выход сборки | `dist/xrRazom_fixes.zip`, `dist/pack.txt`, `dist/notes.md` |
| Выход релиза | git-тег `v<VERSION>` на `GITHUB_SHA`, Release `xrRazom fixes <VERSION>`, ассет `xrRazom_fixes.zip`, отметка latest |
| `build_pack.py` | `validate [--repo DIR]` / `build --version VER [--repo DIR] [--out DIR]` (по умолчанию `--repo .`, `--out dist`); код выхода 0 — успех, 1 — ошибка; `build` без `--version` — ошибка argparse (код 2) |

## Требования

### CI-001 Триггер по путям  [manual]
Workflow ДОЛЖЕН запускаться на `push` в ветку `main` тогда и только тогда, когда push затрагивает хотя бы один путь из списка:
`mods/**`, `pack/**`, `installer/**`, `agent/**`, `.github/workflows/release.yml`, `.github/scripts/**`.
- Дано push в `main`, меняющий только `README.md`, `specs/**` или `host/**`. Когда GitHub обрабатывает push. Тогда прогон не создаётся.
- Дано push в `main`, меняющий `mods/<X>/gamedata/scripts/a.script`. Когда GitHub обрабатывает push. Тогда создаётся прогон.
- Дано push в другую ветку с изменением `mods/**`. Тогда прогон не создаётся.

### CI-002 Ручной запуск  [manual]
Workflow ДОЛЖЕН запускаться вручную через `workflow_dispatch` без входных параметров; такой прогон выполняет те же шаги, что и push-прогон.
- Дано вкладка Actions. Когда пользователь нажимает *Run workflow*. Тогда выполняется полный прогон (проверка, сборка, релиз, уведомление).

### CI-003 Права токена  [manual]
Workflow ДОЛЖЕН объявлять `permissions: contents: write` и НЕ ДОЛЖЕН запрашивать иные права; токен `github.token` используется только для создания релиза.
- Дано файл workflow. Когда читается блок `permissions`. Тогда он содержит ровно `contents: write`.

### CI-004 Последовательность прогонов  [manual]
Прогоны ДОЛЖНЫ выполняться в группе конкурентности `xrrfix-release` с `cancel-in-progress: false`: выполняющийся прогон не отменяется новым, новый ждёт.
- Дано выполняется прогон A. Когда приходит push, создающий прогон B. Тогда A доходит до конца, B стартует после A.
- Дано A выполняется, B ожидает. Когда создаётся прогон C. Тогда B отменяется самим GitHub (в группе хранится не более одного ожидающего прогона), C ждёт A (см. «Открытые вопросы»).

### CI-005 Порядок шагов и прерывание  [manual]
Job `release` (runner `ubuntu-latest`) ДОЛЖЕН выполнять шаги строго в порядке: Checkout → Install LuaJIT / xmllint → Validate → Build zip → Create release → Notify Discord.
Падение любого шага до «Notify Discord» ДОЛЖНО прерывать последующие шаги, кроме «Notify Discord», и делать job неуспешным.
- Дано шаг Validate завершился кодом 1. Когда job продолжается. Тогда Build zip и Create release пропускаются, релиз не создаётся, Notify Discord выполняется, job имеет статус failure.

### CI-006 Установка инструментов  [manual]
Шаг установки ДОЛЖЕН ставить пакеты `luajit` и `libxml2-utils` через `apt-get` и печатать `luajit -v`; ошибка установки ДОЛЖНА валить job.
- Дано apt-get недоступен. Когда выполняется шаг. Тогда job падает до Validate, отправляется уведомление о падении.

### CI-007 Схема pack.json  [auto]
`validate` и `build` ДОЛЖНЫ читать `pack/pack.json` как UTF-8 (BOM `EF BB BF` допускается и отбрасывается) и завершаться с кодом 1 с аннотацией `error` (file=`pack/pack.json`), если:
файл отсутствует; не разбирается как JSON/UTF-8; верхний уровень — не объект; `section` — не строка или пустая/пробельная строка;
`mods` — не массив или пустой массив; элемент `mods` — не строка или пустая/пробельная строка; имя повторяется (сравнение с учётом регистра);
имя содержит `/` или `\` либо равно `.` или `..`. Прочие ключи объекта ДОЛЖНЫ игнорироваться.
- Дано `{"section":"","mods":["A"]}` и существующий непустой `mods/A/`. Когда `validate`. Тогда код 1, аннотация «'section' must be a non-empty string».
- Дано `{"section":"S","mods":[]}`. Когда `validate`. Тогда код 1, «'mods' must be a non-empty array».
- Дано `{"section":"S","mods":["A","A"]}`. Когда `validate`. Тогда код 1, «duplicate mod name 'A'».
- Дано `{"section":"S","mods":["../x"]}`. Когда `validate`. Тогда код 1, «invalid mod name '../x'».
- Дано pack.json с BOM и корректным содержимым. Когда `validate`. Тогда печатается `pack.json OK`.

### CI-008 Сбор всех ошибок pack.json  [auto]
Ошибки `section`, имён модов и папок модов ДОЛЖНЫ накапливаться и выводиться все за один запуск до выхода с кодом 1; ошибки разбора файла, типа верхнего уровня и `mods` ДОЛЖНЫ завершать проверку немедленно.
- Дано `section` пустой и два несуществующих мода. Когда `validate`. Тогда выводятся три аннотации `error`, код 1.

### CI-009 Папки модов пакета  [auto]
Для каждого имени `N` из `mods` ДОЛЖНА существовать папка `mods/N/`, содержащая хотя бы один файл (рекурсивно); иначе — аннотация `error` и код 1.
- Дано `mods: ["A"]`, папки `mods/A/` нет. Когда `validate`. Тогда «pack/pack.json lists 'A' but mods/A/ does not exist», код 1.
- Дано `mods/A/` содержит только пустые подпапки. Когда `validate`. Тогда «mods/A/ is empty», код 1.

### CI-010 Неперечисленные папки модов  [auto]
Папка `mods/D/`, имени которой нет в `mods`, ДОЛЖНА давать аннотацию `warning` «mods/D/ is not listed in pack/pack.json and will NOT be released» и НЕ ДОЛЖНА валить проверку.
- Дано лишняя папка `mods/Old/`. Когда `validate`. Тогда warning, код 0 (при отсутствии других ошибок).

### CI-011 Синтаксис Lua  [auto]
`validate` ДОЛЖЕН проверять каждый файл `mods/**/*.script` (расширение без учёта регистра, включая папки, не перечисленные в pack.json) компиляцией LuaJIT без исполнения (`luajit -b <src> <out>`) после удаления UTF-8 BOM в начале; каждый файл с ненулевым кодом LuaJIT ДОЛЖЕН давать аннотацию `error` (file=`mods/<путь>`) с выводом компилятора, где временный путь заменён на `mods/<путь>`; при хотя бы одной ошибке `validate` ДОЛЖЕН завершаться кодом 1. В конце ДОЛЖНА печататься строка `Lua check: <n> .script file(s), <k> failed`.
- Дано `mods/A/gamedata/scripts/x.script` с `local a = ` (незавершённое выражение). Когда `validate`. Тогда аннотация error для `mods/A/gamedata/scripts/x.script`, код 1.
- Дано корректный скрипт с BOM. Когда `validate`. Тогда ошибок нет.
- Дано скрипт с кодом верхнего уровня, который упал бы при исполнении (`error("x")`). Когда `validate`. Тогда ошибок нет (код не исполняется).

### CI-012 LuaJIT обязателен в CI  [auto]
При `CI=true` (без учёта регистра) отсутствие `luajit` в PATH ДОЛЖНО давать аннотацию `error` «luajit not found (required in CI)» и код 1; без `CI=true` — только `warning` с числом пропущенных файлов и код 0.
- Дано `CI=true`, luajit нет. Когда `validate`. Тогда код 1.
- Дано `CI` не задан, luajit нет. Когда `validate`. Тогда warning «luajit not found - skipping…», код 0.

### CI-013 XML — только предупреждения  [auto]
`validate` ДОЛЖЕН проверять каждый `mods/**/*.xml` на well-formedness (`xmllint --noout`, при его отсутствии — `xml.etree.ElementTree`) и на каждый некорректный файл выводить `warning` «XML not well-formed (non-fatal): mods/<путь>: <первая строка сообщения>»; результат XML-проверки НЕ ДОЛЖЕН влиять на код выхода. В конце ДОЛЖНА печататься `XML check: <n> file(s), <k> warning(s)` (с суффиксом ` [python parser]` без xmllint).
- Дано XML с `#include` вне корня. Когда `validate`. Тогда warning, код выхода определяется только pack.json и Lua.

### CI-014 Проверка файлов установщика при сборке  [auto]
`build` ДОЛЖЕН повторно выполнять проверку pack.json (CI-007..CI-009) и завершаться кодом 1 с аннотацией `error`, если отсутствует любой из `installer/install.ps1`, `installer/install.bat`, `installer/README.txt`.
- Дано нет `installer/README.txt`. Когда `build --version 1`. Тогда «installer/README.txt is missing», код 1, zip не создан.

### CI-015 Версия и тег  [manual]
Шаг сборки ДОЛЖЕН вычислять `VERSION = $(date -u +%Y.%m.%d)-<github.run_number>` и публиковать её как output `version` шага `build`; тег релиза ДОЛЖЕН быть `v<VERSION>`, заголовок — `xrRazom fixes <VERSION>`.
- Дано прогон №7 13.10.2026 по UTC. Когда шаг сборки. Тогда VERSION=`2026.10.13-7`, тег `v2026.10.13-7`.

### CI-016 Состав архива  [auto]
`build` ДОЛЖЕН создавать `<out>/xrRazom_fixes.zip` (DEFLATE, уровень 9; существующий файл перезаписывается) с ровно такими записями, в таком порядке:
1. `pack.txt` (CI-017);
2. `install.ps1`, `install.bat`, `README.txt` — байт-в-байт из `installer/`;
3. для каждого мода `N` в порядке `mods` — все файлы `mods/N/**` как `mods/N/<относительный путь с '/'>` (в порядке обхода `os.walk` с сортировкой подпапок); пустые папки не включаются;
4. если существует `agent/` — каждый обычный файл верхнего уровня `agent/` в сортированном порядке как `agent/<имя>` (подпапки не включаются).
Папки `mods/`, не перечисленные в pack.json, НЕ ДОЛЖНЫ попадать в архив.
- Дано pack.json `["B","A"]`, `mods/A`, `mods/B`, `mods/C`, `agent/x.ps1`, `agent/sub/y`. Когда `build`. Тогда в архиве `pack.txt`, 3 файла установщика, файлы `mods/B/...`, затем `mods/A/...`, затем `agent/x.ps1`; нет `mods/C/...` и `agent/sub/y`.
- Дано любой файл мода. Когда он извлечён из архива. Тогда его байты совпадают с файлом в репозитории.

### CI-017 Формат pack.txt  [auto]
`pack.txt` ДОЛЖЕН быть UTF-8 без BOM с переводами строк LF и завершающим LF, вида:
```
version=<VERSION>
profile=github
section=<section из pack.json, без изменений>
<пустая строка>
[mod] <имя мода 1>
  <sha16>  <путь внутри мода через '\'>
  ...
[mod] <имя мода 2>
  ...
```
где моды идут в порядке `mods`; `<sha16>` — первые 16 hex-символов (нижний регистр) SHA-256 файла; строки файлов отступают двумя пробелами и отделяют хеш от пути двумя пробелами; файлы мода отсортированы по пути с `\` (порядковое сравнение строк, с учётом регистра). Пустых строк между модами нет. Тот же текст ДОЛЖЕН записываться в `<out>/pack.txt`.
- Дано мод `A` с файлами `gamedata/b.txt`, `meta.ini`. Когда `build --version 1`. Тогда `pack.txt` = `version=1\nprofile=github\nsection=S\n\n[mod] A\n  <h1>  gamedata\b.txt\n  <h2>  meta.ini\n`.

### CI-018 Заметки релиза  [auto]
`build` ДОЛЖЕН писать `<out>/notes.md` (UTF-8 без BOM, LF): если `git -C <repo> log -1 --format=%B` успешен и непуст — полный текст сообщения последнего коммита (обрезанный по краям) и пустая строка; затем
`**Состав пакета** (секция «<section>», порядок = приоритет):`, пустая строка, по строке `- <имя мода>` на мод в порядке `mods`, пустая строка,
``Установка: распакуйте `xrRazom_fixes.zip` и запустите `install.bat`.``. Ошибка git НЕ ДОЛЖНА валить сборку (заметки без сообщения коммита).
- Дано каталог без git. Когда `build`. Тогда notes.md начинается со строки `**Состав пакета**`, код 0.

### CI-019 Журнал сборки  [manual]
Шаг сборки ДОЛЖЕН печатать в лог содержимое `dist/pack.txt` и `dist/notes.md` (после маркеров `--- pack.txt ---` / `--- notes.md ---`) и строку `Built <путь>: <n> mod(s), <m> file(s), <b> bytes`, где `m` — число файлов модов (без pack.txt, установщика и agent/).

### CI-020 Создание релиза  [manual]
Шаг «Create release» ДОЛЖЕН выполнять `gh release create "v<VERSION>" dist/xrRazom_fixes.zip --target <GITHUB_SHA> --title "xrRazom fixes <VERSION>" --notes-file dist/notes.md --latest` с токеном `github.token`; релиз не является черновиком и prerelease, единственный ассет — `xrRazom_fixes.zip`. Ошибка `gh` (в т.ч. тег уже существует) ДОЛЖНА валить job.
- Дано успешная сборка. Когда шаг выполнен. Тогда `releases/latest` возвращает новый релиз с ассетом `xrRazom_fixes.zip`, тег указывает на коммит прогона.

### CI-021 Отсутствие релиза при ошибке проверки  [manual]
При неуспешном Validate или Build релиз и тег НЕ ДОЛЖНЫ создаваться, и предыдущий latest-релиз ДОЛЖЕН оставаться latest.
- Дано синтаксическая ошибка Lua в коммите. Когда прогон завершён. Тогда список релизов не изменился.

### CI-022 Уведомление выполняется всегда  [manual]
Шаг «Notify Discord» ДОЛЖЕН выполняться при любом исходе предыдущих шагов (`if: always()`), включая отмену прогона, и отправлять ровно один POST в `DISCORD_WEBHOOK`.

### CI-023 Без секрета — без уведомления  [manual]
Если секрет `DISCORD_WEBHOOK` пуст или не задан, шаг ДОЛЖЕН напечатать `DISCORD_WEBHOOK secret not set, skipping` и завершиться успешно, ничего не отправляя.

### CI-024 Сообщение об успехе  [manual]
При `job.status == success` шаг ДОЛЖЕН отправлять JSON `{"username":"xrRazom fixes","embeds":[{title,url,description,color:5763719,footer}]}`, где:
`title` = `Фиксы xrRazom <VERSION>`; `url` = `<server_url>/<repo>/releases/tag/v<VERSION>`;
`description` = `<первая строка сообщения коммита>` + `\n\n**Состав:**\n` + строки `• <имя мода>` (из `pack/pack.json`, в порядке `mods`, через `\n`) + `\n\nАгент у пира поставит обновление в течение 10 минут (при закрытом MO2).`;
`footer.text` = `опубликовал <github.actor>`.
- Дано push с сообщением «Fix A\n\nподробности». Когда прогон успешен. Тогда описание начинается с «Fix A», без «подробности».

### CI-025 Сообщение о падении  [manual]
При любом статусе job, отличном от `success`, шаг ДОЛЖЕН отправлять `{"username":"xrRazom fixes","embeds":[{title:"Сборка фиксов упала",url:<ссылка на прогон>,description,color:15548997}]}`, где ссылка — `<server_url>/<repo>/actions/runs/<run_id>`, а `description` = `Коммит: <первая строка сообщения коммита>\nРелиз не создан, пир остаётся на прошлой версии.`
- Дано упал Validate. Когда выполнен шаг уведомления. Тогда в Discord красный embed со ссылкой на прогон.

### CI-026 Ручная сборка  [manual]
Если сообщение коммита (`github.event.head_commit.message`) пусто — в том числе при `workflow_dispatch` — вместо первой строки сообщения в CI-024/CI-025 ДОЛЖНО подставляться `Ручная сборка`.
- Дано ручной запуск. Когда прогон успешен. Тогда описание embed начинается с «Ручная сборка».

### CI-027 Сбой уведомления не валит job  [manual]
Ошибка HTTP-запроса к Discord (`curl -fsS`, включая HTTP ≥ 400) НЕ ДОЛЖНА менять статус job: шаг печатает `::warning::Discord notification failed` и завершается успешно; при успехе печатается `Discord notified`.
- Дано неверный URL вебхука. Когда прогон успешен. Тогда job success, в логе warning.

### CI-028 Данные коммита передаются через окружение  [manual]
Сообщение коммита, actor, версия и URL ДОЛЖНЫ передаваться в shell только через переменные окружения и собираться в JSON через `jq --arg`, НЕ ДОЛЖНЫ подставляться выражениями `${{ }}` прямо в текст скрипта (защита от инъекции через сообщение коммита).

### CI-029 Перезапуск прогона  [manual]
Перезапуск (*Re-run*) прогона ДОЛЖЕН использовать тот же `run_number` и тот же коммит; дата VERSION ДОЛЖНА вычисляться заново в момент перезапуска.
- Дано прогон упал на Validate из-за временной ошибки, перезапуск в тот же день UTC. Тогда создаётся релиз с той же VERSION, что была бы у исходного прогона.
- Дано прогон уже создал релиз `v<VERSION>`; перезапуск в тот же день. Тогда `gh release create` падает (тег существует), job failure, отправляется сообщение о падении; существующий релиз не меняется.

### CI-030 Настройки репозитория  [manual]
Для работы ДОЛЖНЫ выполняться условия: GitHub Actions включены; политика организации/репозитория позволяет `GITHUB_TOKEN` получить `contents: write`; правила защиты тегов/rulesets не запрещают создание тегов `v*` от `github-actions`; ветка по умолчанию — `main`. Секрет `DISCORD_WEBHOOK` (Settings → Secrets and variables → Actions → Repository secret) МОЖЕТ отсутствовать (CI-023).

## Ошибки и граничные случаи
- Ошибка в `.script` папки, не перечисленной в pack.json, валит проверку, хотя мод не попадает в релиз (CI-011).
- `CI=true` выставляется GitHub Actions автоматически; локальный запуск `build_pack.py` без LuaJIT проходит с warning.
- Пустые папки модов не попадают ни в zip, ни в pack.txt (mod без файлов — ошибка CI-009).
- Время модификации файлов в zip берётся из checkout, архив не воспроизводим побайтно между прогонами (содержимое файлов — воспроизводимо).
- Падение job по отмене (`cancelled`) тоже даёт сообщение «Сборка фиксов упала».

## Вне области
- Публикация с машины хоста (`host/publish.ps1`) — `publish.md`; установка у пира — `installer.md`, `agent.md`.
- Проверка семантики Lua (существование функций, колбэков) и сверка с файлами GAMMA.

## Открытые вопросы / известные ограничения
1. **Повторный запуск после успешного релиза всегда «падает»** (CI-029): тег уже есть; в Discord уходит «Сборка фиксов упала … Релиз не создан», хотя релиз существует. Нет `--clobber`/проверки существования.
2. **Перезапуск в другой день UTC** даёт другую VERSION, чем показывал исходный прогон.
3. **Отмена ожидающих прогонов**: при трёх быстрых push средний прогон отменяется GitHub (CI-004); последний коммит всё равно будет собран, но отменённый прогон не шлёт уведомление (шаги не выполнялись).
4. **`workflow_dispatch` с любой ветки** создаст релиз на коммите этой ветки и пометит его latest — защиты «только main» нет.
5. **Сообщение коммита**: Discord берёт `head_commit` push-а (только последний коммит при push нескольких), `notes.md` — `git log -1` (тот же коммит). Для ручного запуска notes.md содержит сообщение HEAD, а Discord — «Ручная сборка».
6. **Только `curl` защищён от ошибок** в шаге уведомления: шаг запускается `bash -e`, и сбой `python3` (чтение pack.json) или `jq` уронит шаг и job (на практике после успешной сборки маловероятно).
7. Проверка имён модов не отсекает символы, недопустимые в Windows (`: * ? " < > |`), имена, отличающиеся только регистром, и конечные пробелы/точки — такие моды соберутся, но сломают установку у пира.
8. `section` с переводом строки не отсекается и сломает формат `pack.txt`.
9. В архив попадают все файлы мода, включая служебный `xrrfix_pack.txt`, если он закоммичен в `mods/N/` (установщик его перезапишет).
10. Пути-триггеры не включают `host/**`: изменение только publish.ps1 релиз не создаёт (так задумано — host/ в архив не входит).
