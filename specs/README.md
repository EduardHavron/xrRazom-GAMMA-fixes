# Спецификации (SDD)

Источник истины для поведения репозитория и каждого фикса. Код и тесты следуют спецификации:
сначала меняется спека, потом код, потом тесты, которые ссылаются на ID требований.

**Модель — «живая спека».** На каждый компонент (фикс, мод, часть системы) один документ, и он правится на месте при каждом
изменении поведения; новых документов «под изменение» не заводим. История решений — в `git log` этого файла и в разделе
«История версий» (для сторонних модов). Удалённое требование остаётся в документе зачёркнутым, номер не переиспользуется.

## Структура

```
specs/
  README.md                 этот файл: правила, шаблоны, реестр ID
  system/
    overview.md             общая картина: роли (хост/пир), потоки данных, глоссарий
    repo-layout.md          структура репозитория, pack.json, pack.txt, маркеры, .gitattributes
    publish.md              host/publish.ps1: секция MO2, 3-стороннее сравнение, догон, конфликты, коды выхода
    ci-release.md           GitHub Actions: проверки, сборка xrRazom_fixes.zip, релиз, уведомления Discord
    installer.md            installer/install.ps1: правила секции у получателя
    agent.md                agent/: режим пира, режим хоста, самообновление, планировщик
    spec-check.md           tools/spec_check.py и навык /spec-check: сверка спек, тестов и документации
  fixes/
    <id>.md                 по одному файлу на фикс (имя файла = ID фикса)
```

## Идентификаторы требований

`<ОБЛАСТЬ>-<NNN>`, номера не переиспользуются (удалённое требование помечается `~~зачёркнуто~~ (удалено)`).

| Префикс | Документ |
|---|---|
| SYS | system/overview.md |
| REPO | system/repo-layout.md |
| PUB | system/publish.md |
| CI | system/ci-release.md |
| INS | system/installer.md |
| AGT | system/agent.md |
| CHK | system/spec-check.md |
| FX-<КОД> | fixes/fx-*.md (код фикса, напр. `FX-FETCH-003`) |
| MOD-<КОД> | fixes/mod-*.md (сторонний мод в пакете, напр. `MOD-XXX-005`) |

Каждое требование — одна проверяемая фраза с модальностью **ДОЛЖЕН / НЕ ДОЛЖЕН / МОЖЕТ**.
К требованию — критерии приёмки в виде *Дано / Когда / Тогда*, достаточно точные, чтобы написать по ним тест.
Пометка способа проверки: `[auto]` — покрывается автотестом (ссылка на тест появится позже), `[manual]` — только в игре/вручную.

### Доказательства и `[НЕ ПРОВЕРЕНО]`
Утверждение в «Причине», «Безопасности» и «Ограничениях» опирается на одно из: код (файл и функция), строку лога, проверку
в игре. Если опоры нет — вывод по косвенным признакам, «по истории», поведение C++-части движка — утверждение помечается
`[НЕ ПРОВЕРЕНО]` прямо в тексте. Пометку снимают, когда появилось доказательство (и пишут, какое). `tools/spec_check.py`
считает такие пометки по каждой спеке (CHK-006).

### Проверка в игре
В шапке спеки фикса или мода — поле `Проверка в игре:` с одним из значений:

| Значение | Когда |
|---|---|
| `подтверждено` | исходный симптом воспроизведён в игре до фикса и не воспроизводится с ним; лог-маркер на месте |
| `частично` | проверена часть сценариев (например только у хоста, или нет исходного воспроизведения) |
| `не подтверждено` | проверка в игре показала, что проблема осталась — фикс возвращается к разбору причины |
| `не проводилась` | фикс новый или изменён после последней проверки |
| `не записана` | старый фикс, о проверке нет записи |

Зелёные автотесты не дают `подтверждено`: они проверяют требования на заглушках, а не исходный симптом. После изменения
кода фикса вердикт сбрасывается в `не проводилась`. Что именно проверяли — короткая запись в разделе «Проверка в игре»
(дата, кто, хост/пир, что в логе). Значение дублируется в колонку «В игре» таблицы README (CHK-004).

## Шаблон system-документа

```markdown
# <Название>
Статус: действует | черновик        Код: `путь/к/файлу`

## Назначение
## Термины            (если нужны сверх overview.md)
## Входы и выходы     (файлы, параметры, переменные окружения, коды выхода)
## Требования
### PUB-001 <короткое имя>  [auto]
<Требование.>
- Дано … Когда … Тогда …
## Ошибки и граничные случаи
## Вне области
## Открытые вопросы / известные ограничения
```

## Шаблон спецификации фикса

```markdown
# FX-<КОД>: <название>
Статус: действует | черновик | удалено        Проверка в игре: <см. выше>        Мод: `zz xrRazom Fix - ...`        Скрипт: `gamedata/scripts/<file>.script`[, конфиг: `gamedata/configs/mod_system_<file>.ltx`]
Где ставить: хост | пир | оба        Зависит от: <моды/версии>        Лог-маркер: `[XRRFIX] ...`

## Проблема            (симптом глазами игрока)
## Причина             (точный механизм в коде затронутых модов, со ссылками на файлы/функции, строками лога;
                        без доказательства — [НЕ ПРОВЕРЕНО])
## Решение             (что и куда патчится, точки перехвата)
## Требования
### FX-<КОД>-001 ...  [auto|manual]
- Дано … Когда … Тогда …
## Безопасность         (что происходит без зависимых модов, в соло, на хосте; идемпотентность)
## Вне области / известные ограничения
## Проверка в игре      (пошагово, что должно появиться в логе; ниже — записи о проверках: дата, кто, хост/пир, итог)
```

## Другие моды в пакете

Секция синхронизирует любые включённые моды, не только наши фиксы. Сторонние или переработанные моды перечисляются здесь;
спецификация для них необязательна (если появится — `fixes/<id>.md` с префиксом `MOD-<КОД>`, по шаблону фикса).
Описание от автора мода переносится в его спеку (в «Решение» — устройство, настройки, отладка; можно добавить раздел
«История версий»), а не хранится в папке мода.

Сейчас таких модов в пакете нет: Combined GAMMA NPC Loot Claim и Quantity Craft and Transfer переехали в
[GAMMA-fixes](https://github.com/EduardHavron/GAMMA-fixes).
