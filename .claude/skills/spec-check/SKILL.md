# /spec-check — сверка спек, тестов и документации

Требования к навыку: `specs/system/spec-check.md` (CHK-009). Правила проекта: `CLAUDE.md`.
Навык **ничего не правит**: он собирает отчёт и предлагает исправления; править — только после согласия пользователя.

## 1. Механическая сверка

```bash
git pull --ff-only
python tools/spec_check.py
```

Разобрать каждую находку (уровни `ERROR` / `WARNING` / `NOTE`, коды — в `specs/system/spec-check.md`):

| Код | Что обычно значит | Что предложить |
|---|---|---|
| CHK-001 error | требование `[auto]` без теста | написать тест (имя начинается с ID) или, если требование покрыто тестами другого ID, строку `via <ID>` в `COVERAGE.md` |
| CHK-001 warning | известный `GAP` | напомнить про пробел, если трогали эту область |
| CHK-002 | тест ссылается на несуществующее/удалённое требование | поправить имя теста или вернуть требование в спеку |
| CHK-003 | `COVERAGE.md` отстал | добавить/убрать строки |
| CHK-004 | нет «Проверка в игре» в шапке или README не совпадает | взять значение из спеки (источник истины — спека) |
| CHK-005 | README / реестр не совпадают с `pack.json` | имена — точно как в `pack.json` на момент коммита |
| CHK-006 note | в спеке есть `[НЕ ПРОВЕРЕНО]` | ничего, если не просили; при работе над этим фиксом — спросить, проверено ли |

## 2. Смысловая сверка изменённых спек

Какие спеки смотреть: указанные пользователем, иначе изменённые относительно `origin/main`
(`git diff --name-only origin/main -- specs/`) и незакоммиченные (`git status --short specs/`).
Если изменений нет — спросить, какую область проверить, а не проверять всё подряд.

Для каждой такой спеки:
1. **Шапка.** `Мод:` совпадает с папкой в `pack/pack.json`; перечисленные скрипты/конфиги существуют в `mods/<мод>/`;
   лог-маркер встречается в коде (`grep` по строке из шапки).
2. **Требования против кода.** Для каждого требования найти место в коде мода (`mods/<мод>/gamedata/...`), которое его
   реализует, и проверить условия *Дано/Когда/Тогда*: значения по умолчанию, пороги, имена колбэков, тексты логов.
   Код главнее: если он делает иное, это находка «спека или код» — не решать самому, какая сторона права.
3. **Требования против тестов.** Тест с этим ID действительно проверяет то, что написано в требовании (а не соседнее).
4. **«Причина» и «Ограничения».** Утверждение без ссылки на код (файл/функция), лог или проверку в игре должно быть
   помечено `[НЕ ПРОВЕРЕНО]`. Если пометки нет — находка.
5. **Проверка в игре.** Статус `черновик` при `Проверка в игре: подтверждено` или `действует` при `не проводилась` —
   спросить пользователя, что верно.

## 3. Отчёт

Коротко, по-русски, сначала то, что ломает (ошибки CHK, расхождения спеки с кодом), потом остальное. Для каждой находки:
файл и строка (`specs/fixes/fx-x.md:42`), что не так, что предлагается. В конце — что проверено и что нет (например,
«поведение в игре не проверялось»). Без правок файлов.
